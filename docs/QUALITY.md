# 品質基準 — 「劣らない」の定義

このプロジェクトのゴールは主観的に書かれている（Elden Ring 等に劣らないクオリティ）。
主観のままでは、いつ終わるのか誰にも分からず、改善が進んだのかも分からない。
そこでゴールを**測定可能な13軸**に翻訳し、機械が判定できるようにした。

判定は `node tools/audit.mjs` が行う。合格するまで開発ループが回り続ける。

---

## 判定条件

```
全13軸が 80 点以上 かつ 総合 88 点以上 かつ 未達項目 0 を、連続2回の監査で維持
```

軸の点数だけでは終了条件として甘い。1軸は複数の測定項目の達成率なので、
9項目落としても 85 点＝「80点以上」で通ってしまう。実際それで
「総合97点 PASS・未達10件」という状態が出た。**通ったのに未達が10件ある**のは
判定が壊れているということなので、未達0件を条件に加えた。

連続2回を要求するのは、たまたま通っただけの状態で止めないため。
`docs/AUDIT.md` に履歴が残り、`docs/BACKLOG.md` に未達項目が優先度順で出力される。

---

## 13軸

各軸は複数の測定項目からなる。項目ごとに「目標値」があり、達成率がその軸の点数になる。
目標値は参照タイトル群が実際に持っている規模・深さから逆算している。

### A. 世界のスケールと密度 (weight 12)

広ければ良いのではない。**歩いている間に何かが起き続けるか**が問題。

| 項目 | 目標 | 根拠 |

| 構造物の種類 | ≥ 14 | 拠点が使い回しに見えないこと |

#### 画の解像度

上の帯域は「色が壊れていないか」しか見ていない。**テクスチャのない平坦な
ローポリのフレームでも全部通ってしまう**——実際、一度それで総合100点が出た。
基準として機能していなかったということなので、画に情報が入っているかを
直接測る項目を足した。フラットシェーディングのフレームは、定数色の面が広く、
勾配がほとんどなく、出現する色数が少ない。それをそのまま数える。

| 項目 | 目標 | 意味 |
|---|---|---|
| 表面ディテール（Sobel勾配の平均） | ≥ 0.25 | 面に情報がある |
| 平坦領域率（3x3がほぼ定数の画素） | ≤ 10% | 塗り潰された面が支配的でない |
| 局所コントラスト（8x8タイルのRMS） | ≥ 0.060 | 微細な陰影がある |
| 色の多様性（色相/彩度/明度のビン数） | ≥ 120 | 単色に潰れていない |

ノイズを足せば勾配は上がる。それを防ぐため、勾配と**同時に**平坦領域率・
局所コントラスト・色数を見る。一様ノイズは勾配だけ上げて局所コントラストの
構造を作らないので、4つ揃って動くことが「本当に情報が増えた」条件になる。

空は測らない。滑らかな空のグラデーションは**正しい**もので、それを平坦だと
数えると、夜のシーンが「夜空があるせいで」不合格になり、大気にノイズを
入れる方向に報酬が出てしまう。試されるべきは世界の側なので、測るのも
世界の側にした。

除外は**深度で**行う。画面の割合で切る方式は2回試して2回とも失敗している。
1回目は `gl.readPixels` がボトムアップに返すことを見落とし、捨てたかった側を
そのまま残していた。2回目は向きを直したが、それでも駄目だった——カメラは
約11度上を向いているので真の地平線は画面高67%付近にあり、「下62%」の窓の
3〜5割はどう測っても空になる。深度はどの画素が空かを正確に知っている。
地平線のシルエットは実在する構造なので、近傍9画素のいずれかに地物があれば
採用する。

#### しきい値を引き直した経緯（2026-08-04）

上の「画面下 62%」は、**2026-08-04 まで実装されていなかった**。
`gl.readPixels` は行をボトムアップで返すため、`y` を `0.38h` から `h` まで
走査するコードは画面の**上 62%**——つまり除外したかった空そのもの——を
測っていた。ここまでの数値は全て、地面ではなく空と遠景に対するものだった。

修正すると当然どのシーンの値も上がり、旧しきい値（0.12 / 20% / 0.030）は
全シーンが素通りする。間違った領域に対して較正されていたのだから当然で、
そのまま「合格」にするのは判定を捨てるのと同じなので引き直した。

新しいしきい値は**修正後の全6シーンの中央値付近**に置いてある。
つまり「世界で最も弱い場所が、今の世界の平均程度にはなっていること」を
要求する。絶対値を天下り的に決めるより、この方が意味のある要求になる。

|---|---|
| HDR シーンバッファ | あり |
| 環境遮蔽 (SSAO) | あり |
| 法線マッピング | あり |
| マテリアル種別 | ≥ 10 |
| 動的影 | あり |
| 大気（時間帯・天候・霧） | あり |

### K. 動きの説得力 (weight 10)

但し書きは「モーションキャプチャ」と書いていた。モーションキャプチャが
本当に担っているのは**重さと説得力**であって、記録された人体そのものではない。
手続き生成で同じ役割を果たせるかを測る。

| 項目 | 目標 | 意味 |
|---|---|---|
| 足の接地IK | あり | 斜面で足が地面に沿い、浮きも埋まりもしない |
| 接地誤差（斜面上、m） | ≤ 0.03 | IKが実際に効いていること |
| 骨盤の追従 | あり | 段差で腰が落ちる |
| 二次モーション（慣性・追従） | あり | 停止時に身体が一拍遅れて収まる |
| 注視（look-at） | あり | 頭と胴が対象を追う |
| 加算アイドル層 | あり | 待機が静止画にならない |
| 方向別の被弾リアクション | ≥ 4 方向 | どこから撃たれたか分かる |
| 怯みの段階 | ≥ 3 | 軽い被弾と致命的な被弾が別物 |
| 死亡の変化 | ≥ 3 | 毎回同じ倒れ方をしない |
| 遷移の連続性（最大角速度, rad/s） | ≤ 19 | ポーズが飛ばない |
| ヒットストップ | あり | 当たった瞬間に画が止まる |
| カメラの衝撃 | あり | 重い攻撃で画が揺れる |

遷移の連続性は、**監査中の全フレーム・全リグ**から取る。プレイヤーだけを
90フレーム見ていた頃は 0.364 と出ていたが、その窓の中でプレイヤーは一度も
旋回しておらず、実際に破綻していたのは旋回だった。同じコードのまま全リグを
見ると 0.911 になる（`docs/FALSIFY.md` の5件目）。敵が飛べば敵の飛びが計上
される——プレイヤーだけが見られる特権を持つ理由はない。

ワープしたフレームは別枠で記録し、本値には入れない。地図の反対側へ移された
身体は、その向きへ*回転した*わけではないため。

| 項目 | 目標 | 意味 |
|---|---|---|
| カメラ視線の最大角速度 (rad/s) | ≤ 6.0 | 画面全体が飛ばない |
| カメラのドリー速度 (m/s) | *参考値* | 実装が 7.0 にクランプしている。採点しない |
| ドリーが上限に張り付く割合 | 対照で ≤ 2% | 平地でブームと格闘していない |
| 旋回が上限に張り付く割合 | ≤ 50% | 常時最大速度で振り回していない |
| 実地形での眼の接地クリア (m) | > -0.42 | 眼が丘の中に入っていない |
| カメラ計測フレーム数 | ≥ 300 | 計測が実際に走っている |

ドリー速度が採点対象から外れているのは、**目標がエンジンのクランプより外に
あったから**である。実測は 7.000000000000064 で、`CAM_BOOM_IN = 7.0` の
浮動小数点誤差そのもの。クランプが壊れない限り超えられない項目は、カメラでは
なくクランプを採点している。詳細は下の「目標を、実装のクランプより内側に置く」。

代わりに置いたのは**張り付いている時間の割合**で、これはクランプが縛れない。
一度張り付くのは障害物への反応、三割張り付くのは世界に引きずり回されている。

実地形の接地クリアは、**焼いた世界の最急セル40箇所**を全力疾走させて測る。
スタブ地形ではなく実物なのは、スタブだと見つけた欠陥を「世界はそんな形に
ならない」で却下できてしまうからで、実際この項目は却下できない形で
**眼が地面の 3.086m 下**にいることを示した。ブームは `CAM_MIN_BOOM` より
短くできず、その長さでは全長が丘の中にあるので、短くしても出られない。
直し方は眼を垂直に上げることではなく**ブームの仰角を上げる**こと——眼が球面
上に留まるのでブーム長は変わらず、視線の回転は仰角の変化そのものに等しい。
垂直リフトで解こうとした版は、視線を 20.86 rad/s 回して稼いでいた。

リグに1フレームあたりの上限があるのは「飛ぶ手足は見える」からで、カメラは
同じ欠陥を画面全体で起こす。測るまで、壁の横を歩くとカメラが**1フレームで
19.8m・1.55rad** 飛んでいた（地面クランプが壁の高さを拾って、その天辺に
張り付いていた）。ロックオンの対象切替は 0.76 rad 飛んでいた。13軸のどれも
これを見ていない。

プレイヤーの視点入力はこの上限の外に置く。あれはプレイヤー自身の手であって、
制限すればスティックが引っかかったように感じる。ここが縛るのは**ゲームが
勝手に動かす分**——ロックオンと、疾走時の背後への回り込み。

計測フレーム数を項目にしてあるのは、**駆動しなかった計測は完璧な0を返す**
から。最初に入れたカメラ計測は、プレイヤーが斜面に立ったまま動かない別の
プローブの最中に読んでいて、137フレーム測って 0.0000 と報告した。嘘ではない
——静止したカメラについての正しい数値である。基準側が「実際に走ったこと」を
要求しないと、この種の空振りは合格として通る。

#### 単位を「フレームあたり」から「秒あたり」に直した理由（2026-08-04）

上の項目は当初 rad/frame で書いていた。これは**機械ごとに意味が変わる単位**
で、しかもそれを満たすように作ると、フレームが長い時に動きが遅くなる実装に
報酬が出る。実際そうなっていた——180度の旋回に 60fps で 0.25s、20fps で
0.95s かかっていた。弱い端末では「粗く見える」のではなく**別のゲームになる**。

原因は自分で入れた上限で、`min(RATE*dt, STEP)` の STEP 側が 60fps でも
既に効いていた。STEP は `RATE * MAX_DT`（`MAX_DT` はメインループの dt
クランプ = 0.05s）に置き直した。こうすると dt がクランプされている限り STEP は
決して効かず、クランプ自体が壊れた時だけの保険になる。修正後は 60/30/20fps で
0.283 / 0.200 / 0.250s——差 0.083s で、これは 20fps の1フレームが 50ms で
ある以上、計測の量子化下限に張り付いている。

跳びの判定も rad/s で行う。17ms フレームの 0.27rad と 50ms フレームの
0.82rad は**同じ速さの同じ回転**であり、角度で並べると遅い機械の平常運転が
速い機械の本物の欠陥より上に来る。監査はソフトウェアラスタライザ上で目標
フレームレートの数分の一で走っているので、これは実際に起きる。

## 計測が成立したことを、基準自身が要求する

このプロジェクトで最も高くついた欠陥は、ゲームの欠陥ではなく**計測の欠陥**
だった。しかも3回とも同じ形をしている。

| 何を測っていたか | 出力 | 実際 |
|---|---|---|
| ポーズ連続性を、旋回の無い90フレームの窓で | 0.364 | 0.911 |
| カメラ連続性を、静止したプローブの最中に | 0.0000 | 5.68 |
| 画の統計を、世界を1画素も含まないマスクで | detail 0 | detail 0.69 |

3回とも、**「計測が成立していない」状態の出力が、その計測の正常な値と同じ形**
をしていた。0.364 は妥当な数値に見える。0.0000 は完璧なカメラに見える。
detail 0 は平坦な画に見える。どれも「測れなかった」とは読めない。

したがって基準側に、**計測が実際に行われたこと**を要求する項目を置く。

| 項目 | 目標 | 何を防ぐか |
|---|---|---|
| 各シーンの「画の計測が成立」 | あり | マスクが世界を見つけていない状態での 0 |
| カメラ計測フレーム数 | ≥ 300 | プローブが1フレームも回っていない状態での 0 |
| カメラプローブの旋回量 (rad) | ≥ 1.0 | 回ったが、カメラを一度も動かしていない状態での 0 |

規則として書くと——

> **absence によって falsify できない基準は、走らなかった実行に合格を出す。**

新しい軸を足すときは、その軸が「対象が存在しない」場合と「対象が完璧である」
場合を区別できるかを先に確かめること。区別できないなら、区別できる項目を
一緒に足す。

### 目標を、実装のクランプより内側に置く

上の3件は「計測が成立していない」形だった。4件目は形が違う。**計測は毎回
成立していて、それでも何も測っていなかった。**

`K カメラのドリー速度 (m/s) ≤ 7.2` は毎回合格していた。実測は
**7.000000000000064**。ブームの引き込み速度は適用時点で
`CAM_BOOM_IN = 7.0` にクランプされているので、この数値は 7.0 を超えられない。
クランプが壊れない限り不合格になりようがない。

> **実装側のクランプより外側に置いた目標は、クランプを採点している。**

見分け方は単純で、**実測値が実装の定数と一致していたら疑う**。
7.000000000000064 は 7.0 の浮動小数点誤差であって、カメラがたまたまそこに
落ち着いた値ではない。

厄介なのは、この形が**未測定より見つけにくい**ことである。軸が無ければ表を
見れば気づく。クランプを採点している項目は表にあり、緑で、具体的な数値が
入っている。測っている見た目のまま、何も測っていない。

同じ罠は一段深いところにもある。この項目を「上限に張り付いている**最長時間**」
に置き換えようとして、それも構造的に頭打ちだと分かった——`targetDistance` は
[4.8, 8.4]、床は `CAM_MIN_BOOM` なので、引き込みの最長移動は 7.15m、
7.0 m/s で **1.02秒**。そこでブームは床に着いて張り付きが終わる。1.02秒より
上の目標は発火せず、下の目標は正当な全長引き込みを落とす。**率をクランプで
縛ると、その率での継続時間も一緒に縛られる。**

クランプが縛れないのは**割合**だった。上限に張り付いている時間が全体の何割か
は 0 から 1 まで動ける。一度張り付くのは障害物への反応で、三割張り付くのは
世界に引きずり回されている。これは遊んだときの感触そのものである。

規則としては——

> 新しい数値を基準にする前に、**エンジンがその数値を取れる範囲**を先に出す。
> 目標がその範囲の外なら、採点しているのは実装の定数である。

### 基準そのものを、悪い入力で叩いてみる

上の判定は「定数と一致しているか」という目視でしかない。機械にやらせる形が
一つある——**わざと悪い対象を与えて、基準が反応するかを見る**。

`tools/unit-camera.mjs` の末尾がそれで、ブームを張り付かせる地形と、
半回転を要求し続ける標的をカメラに与え、指標がその範囲の上端まで振れることを
要求する。旋回は 79% まで振れた。ドリーは **0〜12% しか振れず**、弱い指標
であることがそのまま出た。それも書いてある。

この検査は一度、自分の首を絞める形で正しく働いた。ドリーの範囲は当初 23% で、
カメラを直したら 12% に縮んだ。指標が正しく動いた結果だが、同時に警告でも
ある——**昨日のエンジンに合わせて決めた閾値は、昨日のエンジンを測る。**

### 検査地形は、世界が実際に作れる形にする

同じカメラの欠陥は合成地形 `sin(z*1.7)*3.2` でも出た。だがその波長は 3.70m、
高さ場の格子間隔は 4m なので、**世界には表現できない形**である。
「世界はそんな形にならない」で却下できてしまう。

焼いた世界の最急セル40箇所を走らせる検査に置き換えたら却下できなくなり、
眼が地面の 3.086m 下にいることが確定した。

> **検査対象が実物でないと、見つけた欠陥を自分で却下できてしまう。**

世界を焼くのに約1秒かかるが、ゲートに置ける速さであり、払う価値がある。

### フレームをまたいで積算する値について

今日1日で同じ形の欠陥を4箇所で見つけた。カメラのブーム・地面リフト・照準・
距離、リグの向き、リグの地形勾配、アクターの `velY` と `y`。

共通しているのは「**その値がフレームをまたいで積算される**」ことだけである。
`damp()` も `+=` も、一度でも非有限が入ると**その後の全フレームが非有限**に
なる。壊れるのは悪いフレームではなく、その後の全部である。

- カメラが非有限 → ビュー行列が壊れ、何も描かれず、深度も書かれない。
  画面は空だけになる。**症状は「レンダラが壊れた」に見える。**
- リグの向きが非有限 → 全ボーンが NaN。身体が消える。
- アクターの `y` が非有限 → その身体は描画も被弾も攻撃もできなくなる。永久に。

どれも「一度きりの不具合」ではなく「そこから先ずっと」なので、原因の
フレームを特定するのは事実上不可能になる。だから規則にする——

> **フレームをまたいで積算される値は、使う前に有限性を確認する。**
> 上流が非有限を出さないはずだ、は理由にならない。出た場合の代償が
> 「1フレーム変」ではなく「以後ずっと壊れたまま」だからである。

なお、これらは今日の連続性修正で**新たに作り込んだ**ものが多い。硬い
`max()` やクランプを減衰アキュムレータに置き換えると、滑らかさと引き換えに
この性質が付いてくる。置き換えるときは同時に保護すること。

### 単位について

連続性は全て **rad/s・m/s** で書く。rad/frame は機械ごとに意味が変わる単位で、
しかもそれを満たすように作ると「フレームが長いときに動きを遅くする」実装に
報酬が出る。監査はソフトウェアラスタライザ上で目標フレームレートの数分の一で
走っているので、これは実際に起きた（詳細は軸 K の節）。

### 負荷の数値について

三角形数とドローコールは、**ストリーミングが落ち着いてから**測ること。地形
チャンクは1フレームに数個ずつしか構築されないので、早く覗いた計測は「その
瞬間までに届いていた世界」を報告する。同一コミットで 229,045 と 409,347 の
両方が観測されている。低い方が正しいのではない——携帯端末は届いた後の世界を
描くので、**正直な数値は大きい方**であり、低い数値は超過を隠していた。
`tools/diag-perf.mjs` が待ち行列を空にしてから測る。

## 参照タイトルとの関係

この基準は「同じものを作る」ためではない。
参照タイトル群に共通して存在し、**欠けると明確に安っぽくなる要素**を列挙したもの。

- 各軸の目標値は「これを下回ると、そのジャンルのゲームとして成立しない」水準に置いている。
- 物量そのものではなく、物量が担っている**役割**を軸にしている。
  録音された声ではなく「話者がそこにいる感覚」、手で置いた事実ではなく
  「記憶に残る場所」、記録された人体ではなく「重さと説得力」。

### 但し書きについて

以前この文書には「達成しても物量では及ばない」と書いてあった。撤回した。

物量として挙げていた4つ——モーションキャプチャ、手作業のレベルデザイン、
ボイス、テクスチャ——のうち、テクスチャは既に反証されている。画像ファイルを
1枚も持たないまま、素材が素材として光を返すようになった。不可能だったのでは
なく、手をつけていなかっただけだった。

残り3つを軸 K・L・M として測定可能にした。**不可能だと結論するなら、
測ったうえで、なぜ到達できないかを数値で示してからにする。**
