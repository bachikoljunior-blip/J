# 黒鉄の刻印 — KUROGANE

スマートフォンのブラウザで動く、**フル3Dのオープンワールド・アクションRPG**。
エンジンからアセットまで全て自作・手続き生成で、外部ライブラリもダウンロード素材も一切使っていません。

```
index.html を静的サーバーに置くだけ。インストール不要。
```

---

## これは何か

`src/` にあるのは、ゲーム1本と、それを動かすために書いたエンジン一式です。

* **自作 WebGL レンダラ** — シェーダ、シャドウマップ、インスタンシング、ポストプロセスまで自前
* **2.56km × 2.56km の島** — 地形・河川・バイオーム・街道・遺跡・敵配置の全てがシード値から生成
* **ソウルライクの戦闘** — スタミナ、強靭度、ローリング無敵、ガード崩し、パリィ／致命の一撃、ロックオン
* **ボス6体＋ミニボス4体** — HPしきい値で技構成が書き換わる多段階フェーズ制
* **RPG進行** — 7能力値、装備重量によるローリング種別、武器強化+10、護符、魔法、クエスト、会話
* **手続き生成のサウンド** — 適応型BGM、環境音、戦闘SFXを WebAudio で合成

ダウンロードするのはソースコードだけです。総容量は数百KB。

## 世界

アルドラス島は7つの地域に分かれています。地域の位置・標高傾向・敵の顔ぶれ・設置される
セットピースは全て手で設計されていて、その間を埋める地形だけが手続き生成です。
「あの山の向こう」と言ったときに、それが常に同じ意味になるようにするためです。

| 地域 | 推奨レベル | ボス |
|---|---|---|
| 竜草の草原 | 1 | —（野盗の首魁） |
| 囁きの森 | 8 | 森の縛り手 |
| 灰泥の沼 | 14 | 泥の女王 |
| 鉄嶺 | 22 | 鉄の誓約者 |
| 蒼玉の断崖 | 30 | 断崖の竜 |
| 焦土 | 38 | 灰の王 |
| 白牙峰 | 48 | 残り火の王 |

篝火で休息するとHP・FP・聖杯瓶が回復し、代わりに敵が復活します。
死ぬと所持している残り火をその場に落とし、一度だけ回収できます。

## 設計メモ

### レンダリング

WebGL1 の GLSL ES 1.00 で書き、WebGL2 があればそちらを使います（同一ソース）。
1フレームの流れは以下の通りです。

1. シャドウパス（太陽／月からの深度）
2. 不透明パス（地形 → インスタンス → 草）
3. 空（深度テスト付きなので背景ピクセルのみ塗る）
4. 水（波の頂点変位、フレネル、鏡面のきらめき）
5. パーティクル（アルファ → 加算）
6. ポスト（輝度抽出 → 分離ガウシアン → ACES トーンマップ）

キャラクターは全て「箱の階層」です。人型1体で約25個の箱を使いますが、全キャラクター・
全装備を1つのインスタンス化バッチにまとめているため、12体との乱戦でもドローコールは1回です。

メッシュは**頂点ごとの2色ブレンド**を持ちます。1つのインスタンスに主色と副色を渡せるので、
「幹は茶・葉は緑」「壁は木・屋根は藁」を1ドローコールで表現できます。

地域ごとのカラーグレーディング（色調・彩度・周辺減光）を地域影響度でブレンドして
適用しています。境界で切り替えるのではなく混ぜることで、焦土は灰の色に、
白牙峰は冷たく、沼は緑に沈む——同じライティングモデルのまま場所の性格が出ます。

フレームタイムが落ちると内部解像度を自動的に下げます（機能は削りません）。

### アニメーション

キーフレームは1つもありません。ポーズは `(状態, 進行度, 速度, 向き)` の関数です。
毎フレーム、現在のポーズを目標ポーズへ減衰補間するだけなので、
「ダッシュ中に攻撃 → キャンセルして回避」のような遷移が構造的に破綻しません。

骨は「ローカル +Y が骨の向き」という規約で、手足には180°のバインド回転を与えて
下向きに垂らしています。結果として全ての回転が同じ意味を持ちます
（X正 = 前に振る、X負 = 後ろ／上に振る）。

### AI

敵1体ごとに小さな状態機械があり、その上に**攻撃トークン**の共有プールがあります。
トークンがないと、6匹の狼が同じフレームに到達して同時に噛みつきます。それは難易度ではなく
ただの雑音です。トークンがあると1〜2匹が踏み込み、残りは周囲を回る——群れに見えます。

### 音

全て実行時合成です。ファイルがないので、ダウンロードもデコード待ちもありません。
BGMは常時スケジューリングされていて、敵が気づくと戦闘レイヤーが立ち上がり、
ボス戦ではエオリアンからフリジアンへ旋法が切り替わります。

### セーブ

localStorage に3スロット。保存するのは「再生成できないもの」だけです。
地形も木も敵の配置もシード値から復元されるため、セーブデータは数KBで、読み込みは一瞬です。

## 開発

```bash
npm run test       # 起動・描画テスト
npm run gameplay   # システム統合テスト（45項目）
npm run gallery    # 各地域・各ボスの目視確認用スクリーンショット
npm run lab        # 6シーンの露出・コントラスト・彩度を計測
npm run audit      # 品質監査（10軸採点、未達なら非ゼロ終了）
npm run gate       # 2回連続で合格するまで audit を回す
```

**smoke** は Chromium をヘッドレスで起動し、タイトル → キャラメイク → ワールド生成 →
実プレイ → メニュー → 地図 → 戦闘 → セーブまで通しで実行し、コンソールエラーを全て集めて
`tools/shots/` にスクリーンショットを出します。描画統計（ドローコール、三角形数、
フレームタイム）も報告します。

**gallery** は通常プレイなら数時間かかる場所——各ボスの闘技場、海岸線、村、
狼の群れ、嵐——へ順番に飛んで撮影します。他のテストが一度も通らない content にも
必ず目を通すためのものです。

**gameplay** は「ゲームとして成立しているか」を検証します。
世界生成の妥当性（島の海岸線・標高差・全バイオームの出現・拠点数）、
AIがプレイヤーを捕捉して実際に攻撃を当てるか、プレイヤーが敵を倒せるか、
レベルアップ・武器強化・装備重量・護符が数値を正しく動かすか、
ボスが起動してフェーズ移行で技構成と火力が変わるか、
クエストがワールドイベントで進行するか、死亡で残り火を落とし回収できるか、
篝火の回復とファストトラベル、商店の売買、セーブの往復——を全て実行して確認します。

## 「劣らないと判断できるまで作り続ける」仕組み

これは人が眺めて決めることではなく、終了条件として書き下してある。

1. **`docs/QUALITY.md`** — 参照タイトル群に共通して存在し、欠けると明確に安っぽくなる
   要素だけを 10 軸に分解し、それぞれに数値目標を置いた。世界の広さと密度、探索の報酬、
   戦闘の深さ、敵とボスの多様性、進行とビルドの幅、物語と NPC、表現力、性能と応答性、
   操作性、安定性。重み付きで 100 点満点。

2. **`tools/audit.mjs`** — その 10 軸を、ソースの grep ではなく**動いているゲームから**
   測る。コンテンツ数はページ内 `import()` でデータテーブルを直接数え、パリィ・背後刺し・
   状態異常・ガードブレイク・無敵フレームは実際に発生させて確認し、露出とコントラストは
   専用の 320x180 FBO に再合成して読み戻し、ドローコールと三角形数はパス別に集計する。
   安定性は `gameplay.mjs` に委譲する。全軸 80 点以上かつ総合 88 点以上で終了コード 0。

3. **`tools/gate.mjs`** — audit を回す。**2 回連続で合格するまで**終わらない。
   一部の軸はフレーム計測と挙動プローブなので実行ごとに揺れる。1 回の合格は運かもしれず、
   運でしか超えない目標は超えたことにならない。未達なら `docs/BACKLOG.md` に
   影響度順の作業リストが出る。

```bash
npm run gate                                  # 計測だけを繰り返す
node tools/gate.mjs --on-fail "<修正コマンド>"  # 計測 → 修正 → 再計測 のループを閉じる
```

ゲートは測れるがコードは書けない。だから修正側は差し込む形にした。
`--on-fail` を与えると、未達のたびにそのコマンドを実行してから再計測する。
与えなければ計測を繰り返すだけで、これは安定性の確認にしか使えない。

この `--on-fail` は後から足したものだ。最初の版は未達を見つけると
`break` していた——「2回の実行の間に勝手に良くはならない」という理屈で、
それ自体は正しかったが、判断としては間違っていた。
**「基準に達するまで止まらない」ことが仕事のゲートが、止まる側であってはならない。**
今は報告して回り続け、抜ける道は基準到達か試行回数の上限だけになっている
（上限は、無人実行が永久に回らないためだけに存在する）。

### 結果

2026-08-04、**全10軸100点・未達0件で2回連続合格**した。開発の終了条件は満たされた。

未達の推移: 11 → 9 → 5 → 5 → 0。ただし途中で基準側を2回直している。
1回目は「軸80点以上」という条件が甘すぎて「合格・未達10件」が出たので
未達0件を条件に加えた。2回目は計測が空を測っていたバグを直し、
値が上がったぶんしきい値を中央値付近に引き上げた（0.12→0.25 など）。
**基準を緩めた回は無い。** ドローコール上限を90→120にした一件だけは
緩和で、これはキャラクタープリミティブと遮蔽パスのぶんの再配分だと
理由を書いてある。

この仕組み自体が実際にバグを見つけている。毎フレーム 2112 回発生していた NaN 由来の
例外、地形の二重描画、レベル 10 が 4 万必要になっていた経験値曲線、40px を切っていた
タッチ対象、死亡画面を「峰の風景」として測っていた計測バグ——どれも目視では気付けなかった。

そして一番大きかったのは、**この仕組み自体が甘かった**と分かったことだ。
全10軸100点、総合100点を出していたのに、実際の画はテクスチャの無い平坦な
ローポリだった。基準が「色が壊れていないか」しか見ておらず、
「画に情報が入っているか」を一度も見ていなかったからだ。
そこで Sobel勾配・平坦領域率・局所コントラスト・色数の4項目を足した。
足した瞬間に点数は落ちた。落ちるのが正しい。

さらに、その新しい項目から空を外した（画面下62%のみ測る）ところ、
数値は**もっと**悪くなった。それまで測れていたディテールの大半は
空と樹冠の輪郭で、地面そのものは本当に平坦だった、ということだ。
測り方を厳しくするたびに、隠れていた本当の状態が出てくる。

壊れた計測は、そのまま設計判断としても固定化していた。森の配置予算が
草原の半分だったのは「木の下は目を引くものが多い」という根拠のコメント
つきで、そのコメントは空を測っていた頃に書かれていた。結果として森は
島で最もディテールの低い場所になっていた——灰の平原より低い。

同じ経緯で、**このゲームの夕焼けは一度も地平線で燃えたことがなかった**。
空のグラデーションが地平線の時点で既に天頂色へ58%進んでおり、作者が
書いた地平線色が一度も描かれていなかった。傍証は SKY_KEYS の全キー
フレームが霧の色と地平線の色をほぼ同値で書いていること——遠景がフェード
して溶け込む先が空の際の色である、という意図でしか説明がつかない。

中でも一番大きかったのは、**一度死ぬと二度と行動できなくなる**というものだった。
`setState()` は死亡状態をラッチする（死亡モーションが何にも中断されないように、
これ自体は正しい）。ところが復活処理がその `setState()` で待機状態へ戻そうとしていたため、
何も起きていなかった。復活後のプレイヤーは `dead = false` でHPも満タンだが、
状態機械の上では死んだままで、攻撃も回避もガードもできない。
「復活したプレイヤーは再び行動できる」という一行の検査が入るまで、誰も気付けなかった。

## 正直な但し書き

Elden Ring や RDR2 は数百人が数年かけて作ったものです。物量——モーションキャプチャ、
手作業のレベルデザイン、ボイス、テクスチャ——という一点において、これがそれらに並ぶことは
ありません。そこは誠実に認めます。

このプロジェクトが狙ったのは別の軸です。**システムの深さと、手触りの正しさ**を、
ブラウザで即座に起動する数百KBの中に、どこまで詰められるか。
スタミナ管理、強靭度の駆け引き、ローリングの無敵フレーム、パリィの受付、
装備重量とローリング速度のトレードオフ、能力値の軟上限、フェーズで別物になるボス——
このジャンルを「そのジャンルたらしめている」部分は、全部入っています。
