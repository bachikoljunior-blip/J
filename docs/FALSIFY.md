# 「完成した」と言うたびに、それは間違いだった

このプロジェクトは合格判定を6回出している。6回とも、その後に間違いだと
示された。これは反省文ではなく**観測された基礎率**であり、次の合格も
同じ確率で間違っていると考えるべき根拠になる。

## 記録

6回中6回。試行回数は少ないが、方向は一貫している——**合格は「基準が
その欠陥を見ていない」ことの証拠として現れる**。

6回目は、この規則性が偶然でないことを一番はっきり示している。合格が出た
監査は、**カメラを直している最中に走っていた**。走り始めた時点のコードには
壁際で1フレーム19.8m飛ぶカメラが入っており、13軸のどれもそれを見ていない
ので、満点が出た。基準を足したのは合格の後ではなく合格の最中であり、
順序としては「満点 → 別の場所を見たら壊れていた」ではなく
「別の場所を見ていた → その間に満点が出た」である。

つまり合格は、その時点で**測っていた範囲についての正しい報告**でしかない。
範囲の外について何かを言っているわけではないのに、点数の形をしているせいで
全体についての判定に見える。ここが繰り返し引っかかっている場所。

### 5回目が示した別の形

1〜4回目は「軸が無い」誤りだった。5回目は違う。軸はあり、目標値もあり、
未達として正しく赤で出ていた。誤っていたのは**その数値**である。

`0.364` は7回の再計測でビット単位まで同一だった。同一であることを
「安定した実測値」と読んだが、正しい読みは「**同じ狭い窓を7回見た**」
だった。監査は自分で90フレームを駆動してその中だけを見ており、その窓の
中でプレイヤーは一度も旋回していない。実際に破綻していたのは旋回であり、
窓の外にあった。装備自身に全フレーム・全リグを記録させた瞬間、同じコード
のまま **0.911** が出た。

ここから引く教訓は「窓を広げろ」ではない。

- **再現しない数値を残さない。** 0.364 は独立した検証装置で二度再現に
  失敗した。その時点で「計測が間違っている」を第一候補にすべきだった。
  実際には「まだ見つけていない条件があるはずだ」と推測を重ねて数時間を
  溶かしている。空を測っていた3回目と同じ形。
- **値が動かないことは、正しさの証拠ではない。** 決定論的な装備では、
  安定は「見ていない」とも読める。
- **高い数値より、有り得ない数値を疑う。** 0.364 は制限器が保証する上限
  0.27 を超えていた。**保証を超えた時点で、保証の外に経路がある**という
  証明になっていたのに、しきい値との差ばかり見ていた。
- **遅い装備で速い問いに答えない。** ブラウザ監査は1回12分。リグは素の
  JavaScriptで、nodeで直接叩けば2秒。単体で殴った初回に原因が出た
  （`tools/unit-continuity.mjs`）。以後、遅い監査の前に必ず単体を通す。

### 6回目のあと——自分で入れた修正が、別の軸を壊した

カメラに連続性の保証を入れた直後、監査は G 表現力 100→71、H 性能 100→60、
未達21件を出した。`表面ディテール: 0` が6シーン中4つ。**自分の修正で壊した**
と考えるのが自然で、実際そう考えて2つの仮説を立てた。両方とも外れた。

- 仮説「カメラが地面の下に潜った」→ 実測。地面クリアランス 0.46〜1.91m。潜って
  いない。
- 仮説「シーンの画が壊れた」→ 6シーンを撮って開いた。草も木も地形もキャラクター
  も空も、正常に写っている。

どちらも1分で片がついた。同じ問いをブラウザ監査で確かめれば1回12分かかる。
**因果の問いに、遅い装備で答えない**——5回目で学んだはずのことを、もう一度
実地でやった形になる。

そして本当に見つかったのは、探していたものとは別の3つの欠陥だった。

1. **自分が作業していた性質だけを測るテストは、作業していない性質への被害を
   「合格」として承認する。** カメラの単体検査は連続性を8シナリオで測って全部
   緑だったが、「カメラが地面より上にいること」を一度も見ていなかった。硬い
   `max()` クランプを外した時、それを検出する術が無かった。連続性を直して
   正当性を壊しても、テストは何も言わない。
2. **自分をリセットできる指標は、失敗した実行に満点を出す。** カメラ計測は
   479フレーム測って 0.0000 と報告した。同じプローブを単体で走らせると
   8.25 rad/s が出る。`_track` の初期化分岐が実行中に走ると最大値が消える構造
   だった。以後、明示的な `resetTracking()` 以外では最大値を消さない。
3. **単位が間違っている上限は、何も縛っていない。** 照準の移動量を「m/秒」で
   縛っていたが、視線の回転量に効くのは「m ÷ 視点までの距離」である。同じ
   0.32m が、ブーム5mでは 1/16 rad、1.3m では 1/4 rad になる。**それぞれの上限は
   守られていて、唯一意味のある上限だけが破られていた**——0.24 rad の旋回と
   0.32m の照準移動が同じフレームに来て、合計 8.25 rad/s。

3つ目は一般化できる。**複数の上限が同じ予算を食う場合、個別に縛っても全体は
縛れない。** リグはこれを既に正しくやっていた（1つの予算を全ボーンで共有し、
超えたら全体を同じ係数で縮める）。カメラには同じ考え方を持ち込んでいなかった。

### 「測れなかった」を「0」と report する——3回起きた同じ壊れ方

G が 71、H が 60 に落ち、`表面ディテール: 0` が6シーン中4つ。**クリーンな実行で
再現した**ので、機械負荷のばらつきではない。自分がカメラを書き換えた直後だった
ので、当然カメラを疑った。違った。

画は最初から正常だった。共有コードを持たない独立デコーダ
（`tools/png-stats.mjs`）が同じビルドで detail 0.2808 / sat 0.327 / 色 466 を
出し、エンジン自身の `readbackStats` を診断から呼んだ `tools/diag-scene.mjs` は
detail 0.69、マスクは 57600 画素中 25204 を世界と判定した。**壊れていたのは
計測だけ**である。

原因は呼び出しの**順序**だった。監査は `readbackStats` を
`requestAnimationFrame` コールバックの中から呼んでいて、これはゲーム自身の
描画コールバックと同じフレームを奪い合う。動的解像度は変化のたびにシーンの
レンダーターゲットを——深度テクスチャごと——作り直し、作り直された深度
テクスチャは何かが描かれるまで遠平面のままである。描画より前に読むと、
世界マスクは世界を1画素も見つけず、空間統計は全て空集合の平均になり、
detail は `0/1 = 0` になる。

**ここで一度、間違った修正を出している。** 「rAF の外で呼ぶ」ように直した——
つもりだった。直っていなかった。6シーンとも世界画素0のままだった。

`await` の継続はマイクロタスクなので、rAF コールバックの中で resolve した
Promise を await して再開しても、**同じ rAF バッチの中**に留まる。ゲームの
描画コールバックより前か後かは、どちらが先に登録されたかだけで決まる。
診断ツールが正しく測れて監査が測れなかったのは、そのどちらでもない——
**登録順の偶然**である。

`setTimeout(0)` はマクロタスクなので、rAF バッチが全て流れ切るまで走れない。
これで順序が偶然ではなく事実になる。加えて動的解像度自体を監査中は固定した
（`autoResolution = false`）——競合の片側を消す方が、競合に勝とうとするより
確実である。

教訓は「非同期の順序を推論で決めない」。1回目の修正は**もっともらしく、
検証せずに正しいと書いた**。実際には症状が1つも変わっていなかった。

そして `0` は**平坦な画の正当な値**でもある。この2つが区別できなかった。

同じ壊れ方が、このプロジェクトで3回起きている。

| 何を測っていた | 出た数値 | 実際 |
|---|---|---|
| ポーズ連続性を、旋回の無い90フレームの窓で | 0.364 | 0.911 |
| カメラ連続性を、静止したプローブの最中に | 0.0000 | 5.68 |
| 画の統計を、世界を含まないマスクで | detail 0 | detail 0.69 |

3回とも「その計測が成立していない」という状態が、**その計測の正常な値と同じ形**
で出力されている。だから対策は個別の修正ではなく、**計測が成立したことを
それ自体で要求する**ことになる。今回入れたのは3つ:

- `G.yes('画の計測が成立')` — マスクが世界を見つけたか
- `K.ge('カメラ計測フレーム数', 300)` — プローブが実際に回ったか
- `K.ge('カメラプローブの旋回量', 1.0)` — 回った上で、実際にカメラを動かしたか

**absence によって falsify できない基準は、走らなかった実行に合格を出す。**

### 4回目の反証、数値

軸 K・L・M を足した直後の実測。総合は 100 から **85** に落ち、未達は 0 から
**17件**になった。同じコードのままである。変わったのは、何を見るかだけ。

```
A〜J（既存10軸）  100
K 動きの説得力     25   接地誤差 0.194m (≤0.03)、遷移 1.390rad (≤0.35)
L 場所の作家性     67   ランドマーク視認距離 0m (≥400)
M 声                0   全項目ゼロ
総合               85   未達 17 件
```

「不可能」と書いていた3項目が、そのままこのゲームの最も弱い場所だった。
誰も手をつけていなかったのだから当然で、不可能性の証拠ではない。

## だから合格では止まらない

干渉できる事象の全パターンを検証し尽くすことは、現実的な時間では
起こらない。したがって「全て証明した」は到達しない終点であり、
それに近づいたと感じたときは、近づいたのではなく**測っていない領域が
見えていないだけ**だと考える方が、観測と整合する。

`tools/gate.mjs` はこれを実装している。

- 未達があれば `--on-fail` を実行して再計測する（従来通り）
- **未達が0になったら `--on-pass` を実行して再計測する**

合格は終了条件ではなく、**基準を疑う合図**として扱う。
`--on-pass` に渡すのは「今の基準が測っていないものを探して、軸を足す」
作業であって、「祝う」作業ではない。

## 今わかっている「測っていないもの」

合格が出るたびにここへ追記する。これが実質のバックログになる。

- **手触りの時間方向** — 入力から画が動くまでの遅延、先行入力の取りこぼし、
  フレーム落ち時の挙動。今はフレーム時間の分散しか見ていない。
- **長時間プレイの破綻** — 数分の自動プレイしか回していない。メモリの増加、
  数値の桁あふれ、クエスト状態の詰まり、セーブの肥大は測っていない。
- **難易度曲線** — レベル帯ごとの被ダメージ・与ダメージ・死亡率を測って
  いない。「歯応えがある」と「理不尽」を区別できていない。
- **音の内容** — 音が鳴っているかは見ているが、音楽として成立しているか、
  同じフレーズの反復に聞こえないかは測っていない。
- **UIの読解時間** — 要素の最小サイズは測ったが、必要な情報に到達するまでの
  操作数と時間は測っていない。
- **世界の一貫性** — 地名・地形・敵配置・テキストが互いに矛盾しないか。
- **実機** — 全ての性能数値はソフトウェアラスタライザ上の構造的な指標で
  あって、実際の携帯端末で測ったものではない。
- **音の不連続** — バス利得の直接代入は波形の段差、つまりクリック音になる。
  ミュートと音量変更で実際に起きていた（18ms のランプに直した）。他にも
  同種の経路が残っていないかは、まだ機械では見ていない。
- **三角形数・ドローコールの安定性** — この2つは「見た瞬間に何チャンクが
  ビルド済みだったか」を測っており、機械の負荷で変わる。229k と 409k を
  別々の実行で観測している。ゲームの性質ではなく計測の性質かもしれず、
  切り分けていない。
- **自分の修正が別の軸を壊していないか** — 今の運用では、12分の監査を回すまで
  分からない。単体検査は速いが、自分が触った性質しか見ていない。
- **プレイヤーが実際に楽しいか** — これを機械で測る方法を、まだ持っていない。
  現在の基準は全て「欠けていると明確に安っぽくなるもの」の在否であって、
  在れば面白いことを意味しない。ここが最大の未測定領域である。
